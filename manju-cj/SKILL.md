# 漫剧场景与空间三视图

## 项目规则路径

先读取同级 `../manju-shared/PROJECT_RULES.md`，以分镜所属作品的输出目录和作品名运行 `resolve_project.py --work-dir 作品输出目录 --work-title 作品名`；用户另指定规则项目时才传 `--project`。使用返回的规则副本与本作品风格。没有本技能专属参考文件时继续执行以下流程。

## H5 预览与交接数据

每次交付除原有 Markdown 文件外，再保存同名 `.json` 和 `.html`。Markdown 继续遵守本 Skill 原有的正式格式；JSON 采用同级 `../manju-shared/OUTPUT_FORMAT.md` 的结构，`items[].prompts[].text` 必须与 Markdown 中对应的完整 Prompt 或分镜组正文一致。按该文档的 `data` 约定保留本 Skill 的结构化事实与来源，供后续 Skill 读取；不能用摘要替代完整镜头、台词、物品、人物或状态信息。若上游已有 JSON，先核对其组号、来源与原始文件，再复用已确认的字段。

保存 JSON 并通过下述生图检查后运行 `python3 ../manju-shared/render_preview.py 输出文件.json`（从本 Skill 目录解析相对路径，或使用脚本绝对路径），生成同名离线 H5 `.html`。渲染器默认不改写 Markdown。逐项检查 HTML 条目数与 Markdown/JSON 一致、中文可读、手机宽度下不横向溢出，并实际点击一条 Prompt 的“复制”按钮验证复制正文。最后同时给用户 Markdown、JSON 和 HTML 的链接。

生图前读取同级 `../manju-shared/IMAGE_PROMPT_RULES.md`。场景卡继续保留面积依据、未知门轴、凳子原位、来源和制图约定；可复制 Prompt 只写可见空间、已采用的固定布局和当前状态。把“面积：原文称狭小；没有平方米数”改成可见的空间大小感，把“门状态：关闭”改成门扇紧闭；“烟雾状态：无”在空气清晰已可见时省略。凳子位置未确定时不要求它入画；如三视图必须展示，则先确定其位置，不能在 Prompt 中写“原位置未说明”。交付前运行 `python3 ../manju-shared/lint_image_prompts.py 输出文件.json`，修正命中项并同步 Markdown、JSON、HTML。


## 输入和场景识别

完整读取用户指定范围的小说原文、分镜脚本，以及用户提供的当前场景图。建立“原文称呼 → 统一场景名”的代称表，并记录章节、分镜或图片依据。同一地点的内外区域要分开识别；只有空间位置和出入口能对应时才合并代称。仅被一句话提及、未承载剧情或镜头的地点列在附录，不强行生成详细室内场景。

每个主要场景的统一名称至少五个汉字，能区分地点和区域，例如“山间医者居所房内”“山间医者居所门外”。名称不包含可指向特定人物的姓名、称谓或代号；“医者居所”等通用场所功能词可以使用，但不带人物身份指认。人物命名的地名若为原文场所名称，可改用不含人名的功能或空间名称，并在代称表记录对应关系；不要用姓名给场景命名。

## 共用视觉风格

开始生成场景图片 Prompt 之前，读取项目解析结果中的 `style_scene_prompt` 和 `style_file`，核对其属于本作品。将确认的无人场景版完整风格词逐字写入**每一条**场景图片生成 Prompt，包括无人场景图和场景三视图。不能只在文件开头写一次，也不能改写或缩写风格词。该版不得出现五官、发丝、皮肤、服饰、演员等人体词，也不得从原始人物预设带入场景材料没有的建筑、天气和道具。旧版配置缺少场景版时，先按共用规则补齐，不能回退到人物版。

若没有本作品配置，先用 `style_config.py` 展示候选风格并请求确认，再保存到本作品的 `视觉风格配置.json`，然后生成正式 Prompt。用户在当前请求中明确给出并指定风格时，视为本次已确认。若用户明确更换风格，更新本作品配置并标明受影响的 Prompt 需要重新生成。示例文件的风格只用于形成候选，不覆盖用户确认的本作品风格。人物设定板的白色背景不用于剧情场景。

## 空间事实与状态版本

每个场景记录环境类型、时间、氛围、主要特征、面积大小、出入口、门窗、固定家具、主要物品、相邻区域及摄影机轴线。面积有原文数字时照录；只有大小感受时写定性范围；原文与图片都无法确定时写“面积未明确”，不虚构平方米数。将原文事实、分镜补充、图片可见事实和视觉补全分别标注，避免把推测写成事实。

建立一份稳定的空间坐标或布局表。方位若未由材料确定，使用临时的“面向主入口的左侧／右侧”等相对坐标，并明确标记为制图约定。后续所有状态版本和视图都沿用同一坐标、门窗位置、家具位置、物品外形和摄影机轴线。

为每个场景从已知材料选出可持续辨认的固定锚点，如门框、立柱、桌角或路口；写清锚点与出入口、固定家具、可走路径的关系。场景卡另记已知主要光源的位置、方向及其随门窗／昼夜状态变化的依据；不可确认时标“光源方向未明确”，不能为了多机位效果在同一状态制造互相矛盾的光源。把参考图角色分工写在 Prompt 外：场景图用于布局、材质或已可见光线，哪部分仅为制图约定要单列；不要让单张图自动锁定看不见的背面或所有机位构图。

仅为原文、分镜或参考图实际出现的状态创建独立版本，例如门开、门关、灯开、灯关、白天、夜晚。使用同一基础场景 ID 和不同状态名，列出状态变化的精确对象；其余固定结构保持一致。不要笛卡尔组合出材料中从未出现的状态。若状态有发生顺序，记录转变及对应分镜。门扇开启方向、灯具位置等未给出的信息标记待确认，不凭空补出。

场景描述、名称及图像 Prompt **不能包含人名**。图片 Prompt 也不能出现人物、人体、手、人物剪影、人物倒影或人影。需要表达气氛时只描写光线、天气、材质和环境状态，不用人物活动填充场景。

## 场景 Prompt 的风格位置

每个场景状态按顺序输出两个独立 Prompt：第一条为 `无人场景图 Prompt`，在场景环境、时间、氛围、结构、面积和状态描述后完整写入项目的 `style_scene_prompt`；第二条为 `场景三视图 Prompt`，正文必须严格为 `基于已有的场景图片，生成三视图展示全貌`，不得添加风格词、场景描述、机位、视图说明或其他文字。每个场景条目的备注必须包含“需要上传场景图”。未上传场景图时，三视图 Prompt 仍按固定文本输出，但标记待上传，不得声称三视图已生成或360°空间已确认。

## 单场景图 Prompt

为每个场景状态输出可直接复制的“无人物场景图 Prompt”。按照上节约定，在环境和状态描述之后完整写入已确认的共用视觉风格，与人物成稿保持一致。描述环境类型、时间、氛围、主要结构、面积感、门窗与固定道具位置，以及该版本的门、灯、天气等状态。写清摄影机位置、朝向和可见范围。只用源材料支持的细节；视觉补全单独列出且不制造新的房门、窗户、走廊、家具或道具。保持画面真实、可供后续视频生成复用。

## 场景三视图 Prompt 与图片依赖

对每个场景状态，第二条 Prompt 固定为以下单句，保持逐字一致：

```text
基于已有的场景图片，生成三视图展示全貌
```

不得在这条 Prompt 中追加摄影机中心、视图朝向、锚点、布局、风格词、场景名、负面提示词或技术说明。需要补充的视图范围、未知区域、参考图覆盖情况和冲突，只记录在场景资料及 JSON `data.scenes[]`，不拼入第二条 Prompt。

每个条目的 `notes` 必须包含“需要上传场景图”。当前范围没有场景图时，仍保留上述固定 Prompt 作为待执行指令，但把三视图状态标为待上传／未生成；不把它表述成已经完成或确认360°。用户上传场景图后，再用该图执行固定指令并核对场景全貌。单场景图 Prompt 继续依据原文和状态事实独立编写。
## Markdown 输出

输出一份 Markdown 文件，文件名包含作品名、范围和“场景设定”。依次包含：场景索引与代称表、每个场景的基础空间卡、已出现状态及变化表、逐状态无人场景图 Prompt、固定单句场景三视图 Prompt、未确认的区域和冲突清单。每个 Prompt 用独立代码块，方便复制。

交付前逐项核对主要场景覆盖、名称长度、代称合并、面积依据、状态版本是否真实出现、三视图的共同锚点与四周覆盖、所有 Prompt 是否无人物与人名。对缺少依据的四周区域如实标记，避免后续视频生成把推测当成固定场景。
